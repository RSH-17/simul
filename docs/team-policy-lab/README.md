# 팀원용 정책 실험 안내

우리 과제는 10분 안에 벽과 장애물에 붙은 Original ArUco 마커를 찾아 각각 실제 1.5m 안으로 접근하는 것이다. 지도 탐색률과 마커 발견 수를 따로 확인한다. 지금은 `Mixed v1.5.1-balanced`를 기준판으로 보존하고, 벽을 놓치는 문제를 별도 후보에서 비교하고 있다.

이 문서는 2026-11-22 확인한 공유 실험 환경을 설명한다. 현재 실험 결과는 아래 진행 보고와 연결된 원본 보고서를 따른다. 새로운 결과가 나오면 회차 수와 확인 시각을 함께 갱신한다.

## 현재 진행 보고

기준판은 20.15×11.35m 대형 트랙, 상자 5개, 벽 마커 1개와 상자 마커 2개 조건에서 엄격 완주 3/5회였다. 상자 마커 등록·근거리 영상 확인은 9/10, 벽은 3/5였고 범퍼 접촉은 0회였다. 정보량이 적은 벽 구역을 충분히 보지 않는 문제가 남았다. 작은 맵에서 얻은 높은 성공률은 이 대형 트랙 결과와 합산하지 않는다.

최근 후보 `v1.5.1-rescue360`은 처음 360초에 기존 주행을 사용한다. 이후 카메라 미관찰 표면과 미지 공간 정보량을 함께 평가해 이동한 뒤 한 바퀴를 관찰한다. 이미 지도에 나온 벽도 카메라로 확인하지 않았으면 이득이 있다. 마커 판독·접근과 기존 Nav2 안전 검사는 유지한다. 이동 시간에 회전 가감속·영상 대기·여유를 더해 남은 시간에 가능한 목표만 선택한다. 회전 0.5rad/s, 가속도 1rad/s² 기준으로 이동을 제외한 예산은 약 17.6초다.

전환을 30초로 앞당긴 개발 시험에서 실제 Nav2 회전 360.15°와 유효 촬영 갱신 62회를 확인했다. 이 시험은 세 마커 완주에는 실패했으며 기본 360초 정책의 성능 표본에 넣지 않는다. 관련 검사 52개가 통과했고 원본에서도 실패하는 검사 1개는 분리 기록했다.

## 팀원 컴퓨터에서 보드 접속하기

`192.168.252.2`는 현재 호스트의 VM 주소다. 공개 웹 주소가 아니어서 다른 컴퓨터에서 바로 열리지 않을 수 있다. GitHub 저장소가 공개라는 사실과 실시간 보드에 접속할 수 있는지는 별개다. 확인 시 현재 호스트에서 첫 화면과 `/api/runs`는 정상 응답했다. 팀원 기기의 원격 접속은 아직 확인하지 않았다.

현재 호스트에 접근할 수 있는 팀원은 위 보드를 연다. 다른 네트워크에서 보려면 담당자가 Mac의 원격 로그인 계정과 LAN 또는 승인된 VPN 접속 주소를 먼저 공유해야 한다. 그 주소·계정·권한은 이 공개 문서에 넣지 않는다. 공유가 준비되면 팀원 터미널에서 다음과 같이 읽기용 터널을 연다. 계정과 호스트는 담당자에게 받은 실제 값으로 바꾼다.

```sh
ssh -N -L 18780:192.168.252.2:8780 계정@Mac접속주소
```

그 뒤 팀원 브라우저에서 `http://127.0.0.1:18780/`을 연다. 이는 현재 호스트까지 SSH 연결이 되고 그 호스트가 VM에 접속할 수 있을 때의 방법이다. 터널 경유 시작 버튼은 서버의 Host/Origin 검사로 거부될 수 있다. 원격에서는 아래의 준비된 실행 명령을 사용하고, 검사를 해제하지 않는다. 원격 로그인·VPN이나 인터넷 공개 설정을 이번 문서 작업에서 설치한 것은 아니다.

지금 바로 원격 접속이 안 되면 GitHub의 완료 영상과 경로 그림으로 분석에 참여할 수 있다. 실시간 관찰에는 공유 호스트 접속 준비가 필요하다.

## 보드에서 확인하는 순서

1. 진행 중인 카드나 `종료된 시험 모두`를 열고 실행 이름을 확인한다. 최근 후보의 접두사는 `v151-rescue360-track-`다.
2. 카드를 열어 이동 경로·현재 목표·마커별 확정 시각과 접근 상태를 본다. `정답 배치`는 관찰자를 위한 평가용 표시다. 정책 입력에 마커 정답 좌표를 넣지 않는다.
3. RGB 영상에서 마커가 보였던 시각을 찾고 그때 로봇 자세·목표 전환과 연결한다. 발견·ID 등록·실제 근거리 접근은 각각 구분한다.
4. 종료 후 최종 평가와 영상을 확인한다. 보드의 진행 중 거리에는 과대 표시가 관찰됐으므로 최종 거리는 독립 시뮬레이터 궤적에서 계산한 보고서 값을 쓴다.

현재 선택 메뉴에는 일반 Mixed와 Flow v3, R32 Resume 및 예전 후보가 있다. 일반 `Mixed`를 누르는 것만으로 `v1.5.1-balanced`나 `rescue360`이 선택됐다고 판단하면 안 된다. 버전을 지정하는 아래 실행기를 사용하고 실행 이름·소스 manifest·실제 파라미터를 대조한다. 현재 메뉴가 모든 새 후보를 직접 지원하는 것은 아니다.

보드의 `진행 중` 표시는 새 메시지·시뮬 시간도 함께 보고 판단한다. 브라우저를 닫아도 VM의 주행은 계속된다. 시뮬 600초와 실제 600초는 다르며 RTF 0.5이면 10분 시뮬에 대략 20분이 필요하다.

## 준비된 공유 Mac에서 실행하기

실행 담당자 한 명이 큐를 관리한다. 다른 팀원은 같은 시간에 보드를 보거나 별도 Git 브랜치에서 분석한다. 진행 중인 비교의 소스나 VM 작업공간을 덮어쓰지 않는다. 아래 명령은 공유 Mac의 준비된 `osp-jazzy` VM과 동결 맵이 있을 때 사용한다. 새로 복제한 컴퓨터에서 곧바로 실행되는 설치 명령은 아니다.

저장소의 해당 브랜치에서 작은 동결 맵의 기준판을 한 번 실행하려면:

```sh
bash sim-camera.sh v1.5.1-balanced 112301
```

이 실행기는 현재 준비된 환경의 작은 맵을 사용한다. 대형 트랙의 seed 112601~112605와 조건이 다르다. 사용 가능한 seed는 `policy_candidates/2026-11-21_mixed_camera_aware/simulate.sh`에서 검사하며 임의 숫자를 넣어 새 맵을 만드는 명령이 아니다. 공유 시뮬레이터가 사용 중이면 실패 사유를 출력한다.

최근 후보를 같은 대형 트랙의 첫 맵에서 실행하려면 Mac 터미널에서:

```sh
multipass exec osp-jazzy -- bash \
  /home/ubuntu/camera-aware-tools/experiments/2026-11-21_v151_rescue360/run.sh \
  /home/ubuntu/v151-track-five-boxes5-1795247134501974510 \
  --seeds 112601
```

같은 다섯 맵을 모두 비교할 때는 `--seeds 112601`을 생략한다. 이 실행기는 두 공통 잠금이 풀릴 때까지 대기할 수 있다. 같은 명령을 여러 번 보내 큐를 중복 생성하지 않는다. 공유 호스트의 native Gazebo는 최대 두 개이며, 이 비교는 두 잠금을 함께 잡아 한 회차씩 실행한다. 완료된 실패도 보존하고 성공할 때까지 덮어쓰지 않는다.

현재 정식 실험의 읽기 전용 상태 확인은 다음과 같다.

```sh
multipass exec osp-jazzy -- tail -n 15 /home/ubuntu/rescue360-five1121.log
```

실행 후 출력된 `ROOT`와 `START` 경로를 기록한다. 새 실행마다 경로가 바뀐다. 이번 정식 비교 루트는 `/home/ubuntu/v151-rescue360-1795270786287973756`이다. 이것을 새 실행 결과의 경로로 재사용하지 않는다.

## 팀원이 코드를 개선하는 방법

작업할 컴퓨터에서 공유 브랜치를 복제하고 개인 실험 브랜치를 만든다. 쓰기 권한이 없으면 포크에서 작업하고 PR을 만든다.

```sh
git clone --branch codex/mixed-camera-aware --single-branch \
  https://github.com/peter010905/simul.git
cd simul
git switch -c codex/team-wall-experiment
```

팀원별로 마지막 브랜치 이름을 다르게 정한다. 기준판은 `policy_releases/2026-11-21_mixed_camera_sync_v151/`, 새 후보는 `policy_candidates/`, 비교 기록은 `experiments/`에 둔다. 루트 `src`를 고쳤다고 동결 스테이지에 자동 반영되는 구조가 아니다. 실행기가 실제로 읽는 작업공간과 설치 소스를 확인해야 한다.

새 Ubuntu 24.04·ROS2 Jazzy 환경에서는 먼저 기준판 스냅샷의 [빌드 안내](../../policy_releases/2026-11-21_mixed_camera_sync_v151/README.md)를 따른다. Nav2·SLAM Toolbox·Gazebo 등의 의존성이 필요하다. `rescue360`을 별도 빈 경로에 설치하는 예시는 다음과 같다.

```sh
python3 policy_candidates/2026-11-21_v151_rescue360/install.py \
  policy_releases/2026-11-21_mixed_camera_sync_v151 ~/team_rescue360_ws
cd ~/team_rescue360_ws
source /opt/ros/jazzy/setup.bash
colcon build --symlink-install --packages-select osp_mission
```

이 설치는 원본 해시를 검사하고 새 작업공간을 만든다. 빌드만으로 주행이나 보드가 시작되지는 않는다. 대형 트랙 runner는 현재 VM의 맵·헬퍼·고정 작업공간 경로를 사용한다. 팀원 전용 환경에 재현하려면 이 의존성과 경로를 따로 구성해야 하므로 담당자와 먼저 맞춘다. 실시간 8780 보드는 현재 VM에 배포된 비교 서비스이며 이 브랜치의 일반 `dashboard/server.py`와 용도·화면이 다르다.

새 후보는 새 폴더·새 VM 스테이지·명확한 버전으로 설치한다. 실험을 시작한 뒤에는 해당 스테이지를 동결한다. 새 버전의 실행 경로와 이름을 runner에 명시하고 manifest·설정 조회값을 함께 저장한다. 기존 `rescue360` runner를 다른 코드로 몰래 교체해 같은 이름으로 결과를 만들지 않는다.

## 실험 한 회차를 남기는 기준

한 번에 검증할 가설을 하나 정한다. 예를 들어 “지도는 알지만 카메라가 안 본 서쪽 벽이 목표 후보에서 빠지는가”처럼 실패 영상과 결정 로그로 확인할 질문을 쓴다. 코드 변경 전에 기존 성공 동작을 보존할 범위와 실패 판정도 정한다.

비교는 같은 world 파일과 출발 자세·상자·마커 배치, 카메라 480×480·5FPS, 600초 제한을 사용한다. 현재 대형 트랙의 개발 비교 seed는 112601~112605다. 이 다섯 맵에 맞춰 튜닝한 뒤에는 사용하지 않은 맵에서 별도 검증해야 한다. 여러 번 비교한 다섯 맵을 독립 검증으로 부르지 않는다.

| 기록 | 확인 방법 |
|---|---|
| 버전과 실행 조건 | Git commit, 스테이지 경로, 소스 manifest, world SHA-256, 실제 초기 자세·파라미터 |
| 마커 ID·등록 후 접근 | `metrics.json`, 최종 `audit.json`, RGB 증거와 독립 실제 거리 |
| 엄격 성공 | 세 ID·각각 실제 1.5m 접근·기존 근거리 영상 증거·지도 오차 0.25m 이내·범퍼 0회를 함께 검사 |
| 벽과 상자별 성공 | scene의 부착 위치로 구분한 평가 집계, 정답은 평가기에만 제공 |
| 시간·거리·회전·정지 | 시뮬 시간과 실제 시간을 분리, `headings.csv`의 독립 실제 궤적 |
| 재방문·실패 | 목표 선택·취소 사유와 실패 제외 기록. 선택 횟수를 Action 전송 횟수로 단정하지 않기 |
| 회전 관찰의 실행 증거 | `native/rescue360.jsonl`의 실측 각도·유효 촬영 갱신·완료 여부 |
| 카메라 표면 커버리지 | 기존 `viewed` 관찰 메모리와 결정 스냅샷. 전체 실제 표면의 분모·가림까지 포함한 별도 평가는 추가 계측 필요 |
| 원본과 요약 | 모든 실패·중단 사유를 보존. 요약 JSON·경로 그림은 Git, 큰 영상은 Release |

그냥 마커가 잠깐 보였거나 ID가 읽혔다는 것만으로 과제 성공이라고 기록하지 않는다. 낭떠러지·범퍼·스톨·센서 신선도·충돌 검사와 기존 안전 여유를 유지한다. 실물 주행은 별도 준비와 구동 승인이 있을 때만 수행하며 이 시뮬 절차에서 `robot.sh start`를 호출하지 않는다.

## 팀원이 맡으면 좋은 질문

- 상자를 이미 충분히 본 뒤에도 그 주변을 다시 선택하는 이유는 무엇인가?
- 동서남북의 카메라 미관찰 벽이 후보에 남아 있는가? 생성·필터·점수·중단 중 어디에서 빠지는가?
- 먼 마커를 잠깐 봤을 때 테두리 후보·ID 판독·위치 추정·근거리 접근 중 어느 단계에서 끊기는가?
- 6분 전환 뒤 실제 360도 관찰이 누락된 벽과 마커 접근에 도움이 되는가? 이동·회전 비용 때문에 상자 탐색이 나빠지지는 않는가?
- 안전한 경로가 있는데 격자 필터가 거부하는가? 실제 Nav2 계획 결과가 확인되기 전에는 도달 가능하다고 단정하지 않는다.

서로 다른 질문을 맡고 같은 실험 큐에서 비교한다. PR에는 변경 이유, 실행 버전·맵, 실패를 포함한 전후 수치, 해당 영상 시각, 남은 한계를 남긴다.

## Codex에 작업을 이어 맡길 때

다음 내용을 작업 요청에 붙이고 원하는 가설 하나를 덧붙이면 된다.

> 이 저장소의 docs/team-policy-lab/README.md와 AGENTS.md를 읽고 현재 실행 중인 실험을 먼저 확인해줘. Mixed v1.5.1-balanced를 보존하고 별도 후보에서 개선해줘. 실행 중인 스테이지는 수정하지 말고, 실제 launch·설치 소스·로그를 근거로 진단해줘. 공유 보드는 8780이고 일반 Mixed 버튼이 최신 후보라는 보장은 없어. 시뮬 전용으로 같은 대형 트랙 5맵과 같은 조건에서 비교하되 실패도 보존해줘. 지도 정보량과 카메라 미관찰 표면을 구분하고 벽·상자 마커의 ID 등록과 실제 1.5m 접근을 각각 평가해줘. 안전 검사는 유지하고 정답을 정책에 넣지 마. 결과가 나오기 전에 개선됐다고 단정하지 말고, 영상·경로·설정·측정값과 남은 한계를 보고해줘. 실물은 구동하지 마.

공유 호스트 접근 권한이 없으면 먼저 코드와 완료 로그를 분석하고 변경안을 PR로 남긴다. 실제 시뮬레이션을 실행하지 않았으면 그 사실을 결과에 적는다.
