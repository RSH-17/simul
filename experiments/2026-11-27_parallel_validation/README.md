# 두 회차 동시 실행 검증 (2026-11-27)

**새 Gazebo 결과**다. 정책 비교가 아니라, `campaign.py --parallel 2`가 지연 조건을 바꾸는지 확인한 인프라 검증이다.

**결론:** 동시 2회 실행에서 RTF·카메라 fps·프레임 간격·지연 프레임은 혼자 돌린 v1.5.5 20회와 같은 범위였다. 캠페인 실제 시간은 44분 분량을 24.5분에 끝냈다(약 1.8배). 다만 처리 지연 p95와 TF 대기는 원래 두 가지 값(낮음/높음)으로 갈리는데, 동시 실행에서 높은 쪽이 5회 중 4회로 혼자 돌릴 때(15회 중 6회)보다 많았다. 5회로는 우연과 구별할 수 없다. 그래서 **동시 실행을 캠페인에 쓰되, 집계는 `concurrency`로 계속 분리한다.**

| 조건 | 값 |
|---|---|
| 정책 | v1.5.5 먼 벽 슬롯 `~/simul-ws/far-wall-slot`, 소스 지문 `3863093ec823`(기존 20회와 같은 소스) |
| 실행 | `TEAM_SIM_RENDER=system campaign.py --repeats 1 --parallel 2`. 개발 맵 5개×1회, 도메인 174·175 |

| 비교 대상 | [v1.5.5 혼자 실행 20회](../2026-11-26_far_wall_slot/README.md) |

## 타이밍 지표

| 지표 | 혼자 (20회) 중앙값 [최소–최대] | 동시 2회 (5회) 중앙값 [최소–최대] |
|---|---|---|
| RTF | 0.9994 [0.9992–0.9996] | 0.9993 [0.9990–0.9995] |
| 처리 fps (시뮬) | 5.0 [5.0–5.0] | 5.0 [5.0–5.0] |
| 최대 프레임 간격 | 0.20 s [0.20–0.20] | 0.20 s [0.20–0.20] |
| 지연 프레임 `late` | 0 [0–1] | 0 [0–0] |
| 노출 대기열 만료 `expired` | 6 [6–6] | 6 [5–6] |
| 검출기 콜백 p95 (실제 시간) | 5.5 ms [4.8–6.4] | 6.0 ms [5.3–6.8] |
| 처리 지연 p95 (시뮬) | 0.028 s [0.024–0.048] | 0.044 s [0.028–0.048] |
| TF 대기 `tf_waits` | 77 [70–1278] | 564 [70–1190] |

맵별로 보면 처리 지연 p95와 TF 대기는 혼자 돌릴 때도 두 값으로 갈린다. 낮은 쪽은 (약 0.028 s, 약 70회), 높은 쪽은 (0.044–0.048 s, 465–1278회)다. 같은 맵 안에서도 회차마다 다르다. 동시 실행 값은 모두 혼자 실행에서 나온 범위 안에 있었다. 높은 쪽 비율만 다르다(동시 4/5, 혼자 개발 맵 6/15). 이항 확률로 혼자 비율이 그대로일 때 5회 중 4회 이상이 나올 확률은 약 9%다.

## 다음 확인

v1.5.5는 판정 기준에 따라 맵당 5회 이상으로 다시 돌려야 한다. 그 캠페인을 `--parallel 2`로 돌리면 TF 대기 높은 쪽 비율을 더 많은 회차로 확인할 수 있다. 그 결과가 혼자 실행과 같으면 지연 조건이 같다고 기록한다.
